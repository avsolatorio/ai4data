# 7. Quality assurance and documentation of model use

**Question:** How is model use documented and quality-assured?

## Rationale

Official statistics are official because their methods are documented,
their quality is measured and reported, and a named organization stands
behind them. Model assistance enters that framework like any other method. It has
defined points of human decision. Its performance per task is measured
by an evaluation suite. Its versions make a result reproducible. Its
effect on the statistics is assessed. And a statement in the quality
report says where models were used, which ones, how well they performed,
and who decided. A
reader of the report should be able to find every model-assisted step
and its controls, and an auditor should be able to reproduce a run.

## Target state

- Every model-assisted task has defined decision points, an evaluation suite with required scores, and pinned versions recorded per run.
- The effect of model assistance on the statistics is measured (re-coded samples, editor decisions, before-and-after comparisons) and reported.
- Each release's quality report carries a statement of model use with the sections a reader needs, checked for completeness.
- The statements, the suites, and the register are reviewed each year, and the AI-use policy covers production.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Write a statement of model use for one release; name the decision points and the versions. |
| **AI-ready** | Build the evaluation suite per task with required scores; measure the effect on the statistics; publish the statement with every release and check it. |
| **AI-native** | Automate the statement from the register and the suites; audit a run end to end each year; publish the suites' report cards. |

:::info[Running example]
The statement of model use for the labour force survey release names
three model-assisted tasks with their GSBPM sub-processes, the models
and where they ran, the measured performance (coding accuracy on a
re-coded sample, the commentary's verified numbers), the human
oversight at each point, and the effect on the statistics. The check
finds every section and every number it requires.
:::

## Recipes

<Recipe title="7.1 Define the decision points and the suite per task" level="AI-ready" skills="Methodologist; developer" time="One day per task">

**Result:** for every task in the map, a written statement of where a
person decides, an evaluation suite with the scores the task has to
reach, and the versions that make any run reproducible.

1. For each row of the map ([chapter 1](./map.mdx)), write the decision
   point: who decides, on what (the model's output and what else they
   see), and how the decision is recorded.
2. Build the task's evaluation suite as the
   [evaluation cookbook](/cookbook/evaluation-suites/) describes: a
   labelled set, the measures (accuracy by level for coding, editors'
   ratings for explanations, verified numbers for commentary), the
   required scores set from the cost of an error, and the rule that
   changes must pass.
3. Fix and record the versions for every run ([chapter 6](./running.mdx)).
4. Keep the three (decision points, suite, versions) in the register,
   and require all three before a task leaves its pilot phase.

**What this does not do.** These controls cover the tasks in the map. A
task done informally outside it, such as an analyst pasting records
into an assistant, is outside every control. The AI-use policy's rules
and staff training are the remedy for that.

</Recipe>

<Recipe title="7.2 Measure the effect on the statistics" level="AI-ready" skills="Methodologist" time="Half a day per release">

**Result:** for each task, evidence of whether model assistance changed
the published statistics, and by how much, reported with the release.

1. Coding: compare the distribution of codes by major group between the
   automatically coded share and the coder-coded share, and between
   this round and the last, alongside the re-coded sample's agreement.
   A shift larger than sampling variation is investigated before the
   release.
2. Editing: compare what editors decide with proposals shown and
   without, on two comparable samples, to see whether the proposals
   change the decisions.
3. Commentary: the check's record (verified numbers, sourced claims)
   and the measure of how much the draft was edited. Commentary cannot
   change the statistics, and the record shows that it did not.
4. Report these measurements in the statement of model use, with the
   method and the sample sizes.

**What this does not do.** A measured effect within sampling variation
does not prove that there was none. It is the organization's evidence at
the stated precision, which is how every other quality measure is
reported.

</Recipe>

what the effect on the statistics was, checked for completeness before

1. Write the statement from the register, the suites, and the run
   records.
2. Run the check. Publish the statement in the quality report and link
   it from the release page. This meets the transparency requirement of
   the [AI-use policy](/cookbook/ai-ready-dissemination/govern).
3. Keep every statement. The series of statements is the record of how
   model use in production has changed.
4. Once a year, audit one run from end to end: from the statement to
   the register, to the suite's report card, to the job's recorded
   versions, to a result reproduced on the labelled sample.

**What this does not do.** The statement reports. The controls it
describes are what give assurance, and a statement that cannot be
reproduced from the records is what the audit is there to find.

</Recipe>

## Implementation options

- **Decision points and suites:** per task in the register; the evaluation cookbook's methods; required scores from cost of error.
- **Effect measurement:** re-coded samples and distribution comparisons for coding; A/B samples for editing; check records for commentary.
- **Statement:** the template and check in this chapter; published in the quality report; kept per release.
- **Audit:** annual end-to-end reproduction of one run.

## Common mistakes

- **Model use described in a methodology annex nobody updates.** The statement is per release and checked.
- **Performance claimed without sample sizes.** A number without its sample is a claim.
- **Effects assumed to be nil.** Measure them, and report the precision.
- **Controls that exist on paper.** The annual audit reproduces a run.

## Verification

- **Tasks:** every map row has decision points, a suite with required scores, and recorded versions.
- **Effects:** measured and reported per release with sample sizes.
- **Statement:** passes the check; published with each release; the series is kept.
- **Audit:** one run reproduced in the last year with the finding recorded.
