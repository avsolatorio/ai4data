# 7. Evaluation of agent access

**Question:** How is the interface evaluated?

## Rationale

An agent interface has more ways to fail than an API: the model can call
the wrong tool, the right tool with the wrong code, read the right value
and misstate it, answer a question it should decline, or answer without a
citation. None of these shows in the server's logs as an error. The only
way to see them is to run questions with known answers through an agent,
log what it called and what it answered, and score the traces. The
question set of [chapter 1](./purpose.mdx) is the suite; this chapter runs
it.

## Target state

- The question set is run through at least one agent on every change to the server, the tools, the guidance, or the catalog.
- Traces are scored for tool selection, series, value, citation, and behaviour, per language, and the scores are kept with the version.
- A sample of answers is reviewed by a person for wording, caveats, and efficiency.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Try the first ten questions by hand with an assistant connected to the API or the server, and record what went wrong. |
| **AI-ready** | Run the question set through an agent harness that logs traces; score them with the evaluation script; review a sample; keep the results. |
| **AI-native** | Run the suite on every change, per language and per assistant, add logged real questions, and gate publication on the scores. |

:::info[Running example]
Eight questions run through an agent connected to the example server. Six
pass every check. The French question receives an answer with 6.3 percent
where the quarter's value is 6.1, which the value check flags. The regional
question receives a regional figure the series does not have, which the
behaviour check flags: the agent should have declined.
:::

## Recipes

<Recipe title="7.1 Run the question set and log the traces" level="AI-ready" skills="Developer" time="One day to set up the harness; minutes per run">

**Result:** for every question in the set, a record of what the
assistant did: the tools it called, the series it used, the answer it
gave, whether it declined, and how long it took.

Such a record is called a trace. The traces are kept as one JSON
object per line:

| Field | Meaning |
|---|---|
| `question_id` | The question from the set |
| `tools_called` | The tools the assistant called, in order |
| `series` | The series identifier it used, if any |
| `answer` | The final answer text |
| `declined` | Whether the assistant declined to answer |
| `latency_s` | Seconds from question to answer |

```json file=../../website/static/cookbook-files/serving-statistics-to-agents/agent_traces.jsonl
```

1. Connect an assistant (one with tool use, or a small harness built on
   a tool-use API) to the server, with the guidance resource loaded as
   its instructions.
2. Send each question of the set and log the trace in the form above.
3. Run with more than one model where the organization can. Tool
   selection differs between models, and the server's descriptions have
   to work for the assistants users bring.
4. Keep the traces with the date, the server version, the model, and
   the guidance version.

**What this does not do.** The harness runs the organization's
questions through an assistant the organization controls. Third-party
assistants that users bring are observed only through the AI visibility
check of the dissemination cookbook.

</Recipe>

Output for the running example (abridged):

```text
id   lang  tools  series  value  cite  behave  question
a01  en    ok     ok      ok     ok    ok      What was the prevalence of undernourishment in 2024?
a05  fr    ok     ok      FAIL   ok    ok      Quel est le taux de chômage au deuxième trimestre 2025?
a06  en    ok     -       -      -     ok      What is the inflation rate?
a07  en    FAIL   -       -      -     FAIL    What is the under-five mortality rate in the Northern Region?
tools   7/8  0.88
series  6/6  1.00
value   4/5  0.80
cite    6/6  1.00
behave  7/8  0.88
```

1. Read each failure to its cause. Here the French value failure is a
   wrong figure in the answer, which the number check of
   [chapter 4](./provenance.mdx) also catches. The regional failure is a
   missing refusal, which the guidance resource and a `list_code_values`
   call before `get_observations` address.
2. Fix the cause (guidance text, tool description, code-list check,
   catalog field) and re-run. The scores show whether the fix worked.
3. Keep the scores per language and per model with the version.

**What this does not do.** The script scores what the trace records.
Wording, repeated caveats, and the efficiency of the tool calls are read
by a reviewer in recipe 7.3. Eight questions demonstrate; a suite has 30
to 50 per language.

</Recipe>

<Recipe title="7.3 Review a sample and gate changes" level="AI-ready" skills="Subject-matter staff; developer" time="Half a day per run">

**Result:** a measure of answer quality beyond what the script can
check, and a rule that no change to the server goes live if the scores
fall.

1. Draw 20 answers from each run, including some that passed every
   automated check, and score them on a short rubric: right series,
   right number, period and unit stated, caveats repeated, citation
   present, nothing invented, concise.
2. Add every failure to the question set with the expected answer. The
   suite grows from its own failures.
3. Set the gate: a change to the server, the tools, the guidance, or
   the catalog ships only when the automated scores are at or above the
   previous run's, per language, and the reviewed sample shows no new
   kind of failure.
4. Re-run after model updates on the assistants the organization
   operates. A model change is a change.

**What this does not do.** A gate holds the line; it does not raise it.
The scores rise when causes are fixed in the catalog, the API, and the
guidance, which the dissemination cookbook's chapters cover.

</Recipe>

## Implementation options

- **Harness:** an assistant with tool use connected to the server, or a small program on a tool-use API that logs calls; the official SDK's client can drive the server directly.
- **Scores:** tool selection, series, value, citation, behaviour; latency; plus the number check over logged responses.
- **Review:** a rubric and a sample per run; a language model as first-pass grader with human spot checks, as in the dissemination cookbook's chapter 6.
- **Gate:** scores kept per version; publication blocked below the previous run.

## Common mistakes

- **Testing with one model.** Tool selection differs between assistants; the descriptions have to work for several.
- **Scores without causes.** A failed value and a missing refusal need different fixes; the failure list names them.
- **A suite that never grows.** Real questions and real failures are the source of new items.
- **Changes without a re-run.** A one-word change to a tool description changes tool selection.

## Verification

- **Runs:** traces and scores exist for the current version, per language, per model.
- **Causes:** every failure has a recorded cause and a fix or a decision.
- **Gate:** the last change shipped with scores at or above the previous run.
