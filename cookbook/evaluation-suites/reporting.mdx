# 9. Reporting and comparison

**Question:** How are results reported and compared?

## Rationale

A score reported as a number ("Recall@5 is 0.86") invites a comparison
it cannot support: with last quarter, when the set was different; with
another organization, whose set and measures differ; with a published
benchmark, built on other data. A report card states what the number
means: the set version and its size, the slices with their intervals,
the measure definitions, the component versions, the date. Reported this
way, scores can be read across releases, and organizations that adopt a
shared set format can compare, which is how the field learns what is
achievable on official statistics.

## Target state

- Every release of a component carries a report card: pass rates with intervals per slice, the set version and size, the measure definitions, the component versions, and the production scores of the period.
- The organization publishes what it measures about each public AI component and how, in the method documentation.
- Question sets follow a shared format with documentation (a datasheet), so that sets and results can be exchanged where the licence allows.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Report a score per release with the set version and the date. |
| **AI-ready** | Produce the report card with intervals per slice and the versions; publish the measures used for each public component. |
| **AI-native** | Publish report cards with releases; document the sets with datasheets in a shared format; exchange sets and results with other organizations. |

:::info[Running example]
The second run's report card: a pass rate of 0.73 overall with an
interval from 0.57 to 0.90 on thirty questions, and intervals per
language and slice that are wider still. The card states what has to be
published with the numbers for them to be read.
:::

**Result:** a short, fixed-format summary of a run that gives the pass
rate for each slice with an interval around it, and the facts a reader
needs to interpret the rates.

A score alone ("Recall@5 is 0.86") cannot be compared with anything:
the set may have changed since last quarter, and another organization's
set differs. The report card states, with every score, the version and
size of the question set, the versions of the system, the date, and
the interval that says how precise the score is.

The script reads a run file (one row per question with pass or fail,

Output for the running example:

```text
Report card: search-v2-2026-10-01

all                 30      0.73   [0.57, 0.90]
language=en         18      0.83   [0.67, 1.00]
slice=official       8      0.75   [0.38, 1.00]
slice=paraphrase    17      0.76   [0.53, 0.94]
slice=none           5      0.60   [0.20, 1.00]
language=fr          6      0.83   [0.50, 1.00]
language=es          6      0.33   [0.00, 0.67]

Publish with: the question set version, the measure definitions, the model and index versions, and the date.
```

1. Run the script on the release's run file. Add the question set's
   version and size, the definitions of the measures (or a link to
   them), the versions of the system (model, search index, prompt), and
   the date.
2. Add the production scores of the period ([chapter 8](./production.mdx))
   and the gate decision ([chapter 7](./gates.mdx)) with its reason.
3. Add a line with the required score beside the measured score for
   each measure, so that the card says whether the release meets the
   standard set in [chapter 1](./inventory.mdx).
4. Keep the cards with the releases. The series of cards is the
   system's history.

**What this does not do.** The card reports a run. It does not improve
the system, and a card with wide intervals is a reminder that the set
is small, which is [chapter 2](./questions.mdx).

</Recipe>

<Recipe title="9.2 Publish what is measured about each public component" level="AI-ready" skills="Dissemination lead" time="Half a day per component">

**Result:** a public statement, in the organization's method
documentation, of what each public AI component does, how it is tested,
and its latest results.

1. For each public component (the search, the assistant, the agent
   interface), publish four things:
   - what it does and does not do;
   - the measures and an outline of the question set (its size,
     languages, and kinds of question);
   - the headline rates from the latest report card with their
     intervals;
   - the date.
2. State the limits in users' terms: which languages are covered, which
   kinds of question fail most, what the assistant declines.
3. Update the statement with each release and keep the previous ones.
4. Follow the outline of a model card and a datasheet (two widely used
   formats for describing a model and a dataset), so that readers who
   know them find what they expect.

**What this does not do.** A public statement is accountability. The
assurance behind it is the gate and the production review; the
statement reports them.

</Recipe>

<Recipe title="9.3 Use a shared set format and exchange results" level="AI-native" skills="Developer; dissemination lead" time="One day to adopt the format">

**Result:** question sets in a documented, shared format that other
organizations can run, and results that can be compared with theirs.

1. Keep sets in the file formats of this guide and the other cookbooks,
   with the slice fields and the source of each question. Describe each
   set in a datasheet: its purpose, where its questions came from, what
   it contains, how it was labelled, the labellers' agreement, and its
   licence.
2. Publish the sets whose questions and answers are public data
   (catalog questions with expected identifiers) under an open licence.
   Keep sets with confidential content internal.
3. Run other organizations' public sets against the system where the
   catalogs cover similar concepts, and report the results on a separate
   card. Differences between catalogs explain most differences in
   scores.
4. Send new questions and newly found kinds of failure back through the
   program.

**What this does not do.** Comparison across organizations is rough,
because catalogs, languages, and users differ. A shared format makes
the differences visible; it does not remove them.

</Recipe>

## Implementation options

- **Report card:** the script in this chapter plus the versions, definitions, required scores, production scores, and gate decision.
- **Publication:** a page per public component in the method documentation, in model card and datasheet outline.
- **Formats:** the CSV and JSON lines of this guide; a datasheet per set; open licences for public sets.
- **Exchange:** public sets run across organizations; results reported as separate cards.

## Common mistakes

- **A number without an interval.** Thirty questions cannot support two decimals.
- **A card without versions.** The next card cannot be compared with it.
- **Public claims beyond the measures.** Publish what was measured and the limits.
- **Comparisons across organizations read as rankings.** Catalogs differ; the format makes the differences inspectable.

## Verification

- **Card:** every release has one with intervals, versions, definitions, required scores, production scores, and the gate decision.
- **Publication:** each public component has a current statement with the latest headline rates and limits.
- **Formats:** sets are in the shared formats with datasheets; public sets carry a licence.
