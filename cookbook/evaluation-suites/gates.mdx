# 7. Gates on changes

**Question:** How does the suite gate changes?

## Rationale

A suite that reports is read once; a suite that gates is run every time.
The gate is a rule: the same questions through the version before and
the version after a change, the difference per slice, an interval around
the difference that says what thirty or three hundred questions can
decide, a tolerance for regression the organization accepts, and what
happens when a slice is too small to decide. A change that passes ships;
a change that regresses a slice is blocked; a change that may have
regressed a small slice goes to a person, and the set grows there. The
rule is written down and run by a machine, so that it applies to every
change of model, prompt, index, or metadata, including the ones made in
a hurry.

## Target state

- Every change to a component runs the suite before and after, paired by question, with the difference per slice and a bootstrap interval.
- A tolerance for regression is set per component, and a slice whose interval shows a regression beyond it blocks the change.
- Slices too small to decide send the change to a person, and the question set grows in that slice.
- The gate runs in continuous integration, and the component and the set are versioned together.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Run the suite before and after a change by hand; do not ship a lower overall score. |
| **AI-ready** | Pair the runs; compute differences per slice with intervals; set the tolerance; apply the review rule; record every decision. |
| **AI-native** | Run the gate in continuous integration on every change; version the component with the set; report the held-out part separately. |

:::info[Running example]
Two runs of thirty questions. Overall the change gains three points
with an interval from minus seventeen to plus twenty-three; French goes
from two in six to five in six; Spanish drops from four in six to two in
six. Nothing is decidable at thirty questions; the Spanish drop and a
drop on the no-answer questions send the change to a person.
:::

1. Score both versions on the same set version (the scorers of

2. Read the verdicts: a regression beyond the tolerance with the whole

the script says so; the intervals are the honest statement of that. The
answer is more questions in the slices that matter, which is

<Recipe title="7.2 Put the gate in continuous integration" level="AI-native" skills="Developer" time="One day">

**Result:** every change to the component's code, prompts, index, or
configuration runs the gate automatically, and a blocked gate stops the
change from reaching production.

1. Keep the question set, the scorers, the required scores, and the
   tolerance in the component's repository, versioned with it.
2. On every change, run the suite on the previous and the new version
   (or against the stored scores of the previous version on the same set
   version) and the comparison; fail the pipeline on BLOCKED, hold on
   REVIEW with the output attached for a person.
3. Report the held-out part separately, so that a change tuned on the
   development part is seen on questions it never touched.
4. Store the run files and the decision with the change, so that a
   regression found later can be traced to the change that passed it.

**What this does not do.** A gate protects what the set covers. A
change that breaks a question type the set lacks passes, which is why
the production review of [chapter 8](./production.mdx) feeds the set.

</Recipe>

<Recipe title="7.3 Decide the review cases and grow the set where they occur" level="AI-ready" skills="Head of the unit; dissemination staff" time="An hour per review case">

**Result:** a recorded decision for every change the gate sent to
review, and more questions in the slice that could not decide.

1. For a REVIEW verdict, a person reads the failed questions of the
   slice with the answers before and after; a change that fixes one
   kind of question and breaks another is a change to split.
2. Decide: ship with the regression accepted and recorded, ship after a
   fix, or hold; record the decision with the reason.
3. Add questions to the slice that could not decide, from logs and from
   native speakers, so that the next change is decidable there.
4. Review the tolerance and the required scores each period from the
   decisions.

**What this does not do.** A review case is a judgement; the record of
judgements is what makes the next one consistent. The set growth is the
only thing that reduces the number of review cases.

</Recipe>

## Implementation options

- **Comparison:** the script in this chapter; paired bootstrap on per-question outcomes; a tolerance per component.
- **Verdicts:** BLOCKED (interval below the tolerance), REVIEW (drop beyond the tolerance, too few questions), PASS.
- **Integration:** the gate in the repository's continuous integration; run files and decisions stored with the change; the held-out part reported separately.
- **Records:** decisions with reasons; tolerance and required scores reviewed per period.

## Common mistakes

- **Comparing different question sets.** The difference is then between sets; pair by question on one set version.
- **A gate on the overall score.** The slice that broke is invisible.
- **No tolerance.** Every change regresses something by one question; the tolerance says what matters.
- **Review cases decided and not recorded.** The next decision contradicts the last.

## Verification

- **Pairing:** every comparison is on the same set version with per-question pairing.
- **Verdicts:** per slice with intervals; BLOCKED and REVIEW produce the stated actions.
- **Integration:** the gate runs on every change; decisions and run files are stored with the change.
