# 1. Purpose and limits of synthetic data

**Question:** What are synthetic data for, and what are they not for?

## Rationale

Synthetic microdata are records generated by a model fitted to the real
microdata, so that they look like the real file (the same variables,
similar distributions and relationships) while containing no real
person's record. They answer a need every microdata team has. Users want to write and
test code before applying for the licensed file. Students need a
realistic file. Researchers want to develop a method. Developers need
test data for a pipeline. Partners cannot receive the real data. They do not answer the need for estimates:
a statistic computed from a synthetic file is a statistic about the
synthesizer, and the organization publishes nothing from one.

Two kinds exist. A fully synthetic file replaces every value; a
partially synthetic file replaces the sensitive variables and keeps the
rest. The first protects more and preserves less; the second is a
disclosure control method for a public use file, documented as such.
This guide concerns fully synthetic files for sharing, with the methods
and measures that make them useful and safe, and it keeps the question
of estimation out of scope by design.

## Target state

- The organization has a written statement of what synthetic files are for and what they are not for, and every synthetic file carries it.
- The decision to produce a synthetic file is taken from demand (access requests, teaching, development needs) and recorded with the intended uses.
- Synthetic files are labelled as synthetic in their name, their record, and their data, and are never a source of published statistics.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Write the purpose statement; produce one synthetic file for the most requested survey for code development and teaching. |
| **AI-ready** | Produce synthetic files for the main surveys with measured utility and risk, documented records, and a place in the access workflow. |
| **AI-native** | Produce synthetic files at each release as a pipeline stage, with relational structure where the survey has it, and track their use. |

:::info[Running example]
The example organization's labour force survey is its most requested
microdata file. Applicants wait weeks for the licensed file and then
discover that their code does not run on it. A synthetic file of the
same shape, downloadable at once, lets them write and test their code
first. The recipes of this guide produce, measure, document, and release
that file; a 300-record extract with six variables carries the scripts.
:::

## Recipes

<Recipe title="1.1 Write the purpose statement" level="Foundational" skills="Head of the microdata unit; methodologist" time="Half a day">

**Result:** a short, approved, published statement of what the
organization's synthetic files are for and what they must not be used
for.

1. List the intended uses: writing and testing analysis code before
   applying for the real file; teaching; developing methods; testing
   software and pipelines; demonstrations.
2. List the prohibited uses and the limits: no estimation or
   publication of statistics from a synthetic file; no use as a
   substitute for the real microdata; no guarantee that relationships
   hold beyond those the utility report lists; no reliability for small
   groups.
3. State the labelling rule: every synthetic file is marked as
   synthetic in its name, in its catalog record, and inside the data
   itself.
4. Publish the statement with the access policy of the
   [microdata cookbook](/cookbook/microdata-documentation/access), and
   repeat it in every synthesis record ([chapter 6](./release.mdx)).

**What this does not do.** A statement sets expectations. Users will
still compute things from a synthetic file; the label, the record, and
the utility report are what tell them how far to trust the result.

</Recipe>

<Recipe title="1.2 Decide which files to synthesize, from demand" level="Foundational" skills="Microdata unit" time="Two hours">

**Result:** an ordered list of the surveys to synthesize, with the
demand behind each and the uses the synthetic file would serve.

1. Count, for each survey, the access requests over the last two years,
   the requests from teachers, and the internal needs (pipeline testing,
   training).
2. Order the surveys by demand. Start with one survey whose real file
   has a queue of applicants.
3. For each survey, write down the intended uses and the variables
   those uses need. A teaching file needs the shape of the whole
   questionnaire; a file for testing code needs the variables and types
   users will write code against.
4. Record the list in the microdata unit's work plan.

**What this does not do.** Demand decides the order of work. Whether a
survey's synthetic file is good enough to release is decided by the
measures of [chapters 3](./utility.mdx) and [4](./risk.mdx).

</Recipe>

<Recipe title="1.3 Separate synthesis for sharing from disclosure control" level="Foundational" skills="Methodologist; disclosure control unit" time="Two hours">

**Result:** a clear line, in the policy and in practice, between fully
synthetic files made for sharing and partially synthetic methods used
to protect a public use file.

The two are easy to confuse because the methods overlap. A fully
synthetic file replaces every value and is never used for estimates. A
partially synthetic file replaces only sensitive variables, keeps the
rest, and is a form of disclosure control applied to a public use file
that users do analyse.

1. State in the policy that the files of this guide are fully synthetic
   and are not public use files: nobody estimates from them, and their
   risk assessment ([chapter 4](./risk.mdx)) concerns copying and
   inference, never the identification of a respondent in the file.
2. Where the organization uses partial synthesis as disclosure control,
   document it in the public use file's disclosure control record
   ([microdata cookbook, chapter 8](/cookbook/microdata-documentation/access)),
   with utility measured for the estimates users will make.
3. Keep the two products apart in the catalog, with different labels,
   records, and terms of use.

**What this does not do.** The line keeps users and reviewers clear
about what each file is. A team that masters one method learns the
other; what differs is the documentation and the use.

</Recipe>

## Implementation options

- **Kinds:** fully synthetic for sharing (this guide); partially synthetic as a disclosure control method (documented with the public use file).
- **Statement:** a page with intended uses, prohibited uses, limits, and the labelling rule, published with the access policy.
- **Prioritization:** access requests, teaching and development needs, variables required by the uses.

## World Bank examples

- The program's synthetic data workstream develops [REaLTabFormer](https://github.com/worldbank/REaLTabFormer), a transformer-based generator for tabular and relational data, placed under disclosure control (GSBPM 6.4) in the [GSBPM mapping](/docs/gsbpm-mapping).
- The [Microdata Library](https://microdata.worldbank.org/) access tiers and the [microdata cookbook's access chapter](/cookbook/microdata-documentation/access) set the workflow a synthetic file joins.

## Resources

- [UNECE, Synthetic Data for Official Statistics: A Starter Guide](https://unece.org/statistics/publications/synthetic-data-official-statistics-starter-guide): the reference introduction for statistical organizations, with use cases and cautions.
- [REaLTabFormer](https://github.com/worldbank/REaLTabFormer): the program's generator for tabular and relational synthetic data (MIT).

- [Access chapter of the microdata cookbook](/cookbook/microdata-documentation/access): the access policy and tiers the synthetic file sits beside.

## Common mistakes

- **Synthetic files used for estimates.** The statement and the label exist to prevent it, and the organization never publishes one.
- **Synthesis as a replacement for disclosure control.** Different product, different record.
- **Files synthesized because the tool exists.** Demand orders the work.
- **Unlabelled files.** A synthetic file that looks real is used as real.

## Verification

- **Statement:** approved, published, and repeated in every synthesis record.
- **Prioritization:** the list exists with demand figures and intended uses.
- **Separation:** synthetic files and public use files have distinct labels, records, and terms in the catalog.
