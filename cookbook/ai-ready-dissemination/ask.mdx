# 4. Natural-language access

**Question:** Can users ask questions in their own words?

## Rationale

Most users do not know the official names of indicators or the structure of a
catalog. They type a question. Natural-language interfaces reduce the effort of
finding and reading statistics, and they are the form in which many users
already meet AI systems.

This chapter comes after findability, retrieval, and meaning because a
conversational interface depends on all three. A chatbot placed over incomplete
metadata produces confident answers from poor inputs.

## Target state

- A question returns the relevant series, with the unit, period, and source, in a few seconds.
- The system says when it has no matching data.
- Users can ask in the languages they use.
- The system's role is clear: it finds and explains published statistics and does not create new ones.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Provide search with filters by topic, geography, and period. Add example queries on the search page. Review the logged search terms that returned no results. |
| **AI-ready** | Add semantic search that matches by meaning ([chapter 1](./find.mdx)). Return structured answers that link to the series pages. Support the main user languages for queries. |
| **AI-native** | Offer a conversational interface that uses retrieval-augmented generation: it retrieves records and values first, and the language model writes the answer from them. Answers carry citations and numeric checks ([chapter 5](./trust.mdx)). |

:::info[Running example]
A user asks "Is hunger going down?" The system retrieves
`FS_UNDERNOURISH_PCT` and its last three values, and the model answers from
those values only: 8.4% in 2022, 7.9% in 2023, 7.6% in 2024, with the series
URL. For "What is inflation?" it says that the organization does not publish that
series.
:::

## Recipes

<Recipe title="4.1 Review failed searches every month" level="Foundational" skills="Dissemination staff" time="Two hours a month">

**Result:** the most common ways users fail to find data are known and fixed
at the source, and each one becomes a test question.

1. Export the search queries that returned zero results, or whose results were
   not clicked, for the last month.
2. Group them by intent. Most fall into a few buckets: a synonym the catalog
   does not use ("jobless"), a language the catalog does not cover, a series
   the organization does not publish, or a typo.
3. For synonyms, add the words to the description or a keywords field of the
   right series. For missing languages, translate the titles of the series
   involved. For unpublished series, add a page that says so and points to
   the nearest series.
4. Add each query with its expected series to the question set
   ([chapter 6](./evaluate.mdx)). The next monthly score shows whether the fix
   worked.

**What this does not do.** Zero-result queries show what users looked for and did not find. Queries that returned wrong results and were clicked anyway are invisible here; the answer review of recipe 4.3 and the question set of [chapter 6](./evaluate.mdx) catch those.

</Recipe>

<Recipe title="4.2 Answer from retrieved records only" level="AI-native" skills="Developer with access to a language model and the API from chapter 2" time="One week for a prototype">

**Result:** an assistant that answers questions with values from the API and
cites the series, and that declines when nothing matches.

The flow has four steps, and the model sees data only in step 3:

1. **Retrieve.** Run the question through the catalog search (recipe 1.3) and
   take the top three series.
2. **Fetch.** Call the API or MCP tool for the values of those series, with
   unit, release, and source URL.
3. **Generate.** Send the question and the retrieved material to the model
   with instructions like these:

```text
You answer questions about official statistics published by the organization.
Use only the records and values provided below. Every number you state
must appear in the values. Cite the series id and source URL for each
number. State the unit and the period. If the records do not answer the
question, say that the organization does not publish a matching series and do
not estimate. Answer in the language of the question.

Records:
[series records as JSON]

Values:
[values as JSON]

Question: [user question]
```

4. **Verify.** Run the answer through the numeric check from
   [chapter 5](./trust.mdx) before showing it. Show flagged numbers as
   unverified or remove them.

Log the question, the retrieved records, the answer, and the verification
result for the monthly review (recipe 4.3). Tool-use APIs and MCP let the
model call the data tools itself; the rules above still apply.

**What this does not do.** The flow grounds answers in retrieved records and cannot answer better than the retrieval. A question whose series is outside the top three gets a wrong or declined answer, which is why the retrieval scores of [chapter 6](./evaluate.mdx) are tracked beside the answer scores.

</Recipe>

<Recipe title="4.3 Review a sample of answers each month" level="AI-native" skills="Subject-matter staff" time="Half a day a month">

**Result:** a measured error rate and a list of fixes, in place of anecdotes.

1. Draw 30 logged answers at random, including some in each language.
2. Score each against four questions: right series, right numbers, right
   period and unit, right caveats. Record yes or no for each.
3. Add every failure to the question set with the expected answer.
4. Report the four rates each month next to the retrieval scores.

**What this does not do.** Thirty answers a month show large error rates; a rate below a few percent needs a larger sample to be seen. The sample is of logged answers, so questions users did not ask are not covered, and the question set of [chapter 6](./evaluate.mdx) supplies those.

</Recipe>

## Implementation options

- **Search first:** a good semantic search page already answers many questions and carries lower risk than free-text generation.
- **Retrieval-augmented generation (RAG):** retrieve metadata and values from the authoritative source, then ask the model to answer only from what was retrieved. Return the retrieved records with the answer.
- **Tool use:** let the model call the data API or an MCP server for values, so that numbers come from the source.
- **Multilingual access:** use multilingual embedding models for queries, translate metadata for the priority languages, and test each language separately.
- **Model choice:** small and open models can handle routing and rephrasing tasks. See [chapter 9](./sustain.mdx).

## Common mistakes

- **A chatbot as the first AI project.** Without chapters 1, 2, 5, and 6 in place, the errors are invisible until a user reports them.
- **Letting the model answer from memory.** Models have seen old versions of many statistics. Values must come from the API in the same request.
- **Testing in one language.** A system that works in English can fail completely in the national language. Score each language.
- **No refusal path.** A system that always answers will invent a series when none exists.

## Verification

- **Question set:** collect real questions from help-desk and search logs, and add questions in each supported language.
- **No-answer cases:** include questions the organization cannot answer, and check that the system declines.
- **Review sample:** recipe 4.3.
