# 2. Make your data retrievable

**Question:** Can AI retrieve our data reliably?

## Why this matters

An AI system that cannot reach the numbers will use whatever it can reach,
such as an outdated table in a PDF, a copy on a third-party site, or a
remembered value from its training data. Reliable retrieval means the
authoritative values are available in a form that software can request
directly.

Data locked in PDFs, scanned tables, or interfaces that need a person to click
through forms are the most common barrier.

## What good looks like

- Data are available in open, structured formats.
- Every series, dataset, and release has a stable identifier that does not change when a page is redesigned.
- A documented interface lets software request a specific series, geography, and period.
- Responses include the values together with their unit, period, and source.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Publish data as CSV or another open format in addition to Excel and PDF. Use one tidy layout per file, with one header row and consistent codes. Keep download URLs stable. |
| **AI-ready** | Provide a documented REST API with an OpenAPI description. Support filtering by series, geography, and period. Return units, period, and a source URL with the values. Publish a bulk download. State the terms of use and rate limits. |
| **AI-native** | Expose an MCP server so AI assistants can discover and call data tools through a standard protocol. Return provenance with every response. Document which tools are read-only. |

:::info[Running example]
The example office publishes its values as one tidy CSV whose columns are
SDMX cross-domain concepts, describes a three-endpoint API in OpenAPI, and
wraps the same data in an MCP server with two read-only tools.
:::

## Recipes

<Recipe title="2.1 Publish tidy CSV files at stable URLs" level="Foundational" skills="Data manager" time="One day to set the convention, then part of each release">

**Result:** one file per series, in a layout that any tool can read, at a URL
that does not change between releases.

1. Use one row per observation and the same columns for every series. Name
   the columns with the SDMX cross-domain concepts from the
   [Content-Oriented Guidelines](https://sdmx.org/guidelines/): `REF_AREA`,
   `TIME_PERIOD`, `OBS_VALUE`, `OBS_STATUS`, `UNIT_MEASURE`. The file then
   maps directly to an SDMX data structure, and SDMX tools and the
   [SDMX-CSV](https://sdmx.org/) format use the same names.

```csv file=../../website/static/cookbook-files/ai-ready-dissemination/example_values.csv
```

2. Keep codes in the file (`NAT`, `2025-Q1`) and put labels in the code lists
   ([chapter 3](./understand.mdx)). Use UTF-8, a period as the decimal
   separator, and ISO 8601 dates and SDMX period formats.
3. Fill `OBS_STATUS` from the SDMX observation status code list: `A` for a
   normal value, `P` provisional, `B` break in series, `E` estimated. The
   example marks the latest quarter of unemployment as provisional.
4. Publish each series at a predictable path, for example
   `/series/FS_UNDERNOURISH_PCT/data.csv`, and the whole catalog as one bulk
   file. When a new release replaces the file, the URL stays the same and the
   `RELEASE` column changes.
5. Offices that run an SDMX web service can publish SDMX-CSV from it
   directly. For files outside SDMX, describe the columns once with a
   [Frictionless table schema](https://specs.frictionlessdata.io/table-schema/)
   or [CSV on the Web](https://www.w3.org/TR/tabular-data-primer/) metadata,
   so that tools know the column types.

</Recipe>

<Recipe title="2.2 Describe the API with OpenAPI" level="AI-ready" skills="Backend developer" time="One to two days for an existing API">

**Result:** a machine-readable description of the API that developers and AI
systems can read, and a response format that always carries unit, period,
and source.

Offices that run an SDMX web service already have a documented interface:
the [SDMX REST API](https://sdmx.org/) specification, with SDMX-ML,
SDMX-JSON, and SDMX-CSV responses. The World Bank publishes the World
Development Indicators this way through its
[SDMX API](https://datahelpdesk.worldbank.org/knowledgebase/articles/1886701-sdmx-api-queries).
The steps below are for an office with a custom REST API.

1. Start from the minimal description below. It has three endpoints: list
   series, get one series, get observations. Series records use the field
   names of the World Bank indicator schema and data responses use SDMX
   concept names, so the API speaks the same vocabulary as the files.

```yaml file=../../website/static/cookbook-files/ai-ready-dissemination/openapi_minimal.yaml
```

2. Make every data response carry `SERIES`, `UNIT_MEASURE`, `RELEASE`, and
   `SOURCE_URL` at the top level and `OBS_STATUS` on each observation:

```json
{
  "SERIES": "FS_UNDERNOURISH_PCT",
  "UNIT_MEASURE": "% of population",
  "RELEASE": "2025-03-14",
  "SOURCE_URL": "https://stats.example/series/FS_UNDERNOURISH_PCT",
  "observations": [
    {"REF_AREA": "NAT", "TIME_PERIOD": "2023", "OBS_VALUE": 7.9, "OBS_STATUS": "A"},
    {"REF_AREA": "NAT", "TIME_PERIOD": "2024", "OBS_VALUE": 7.6, "OBS_STATUS": "A"}
  ]
}
```

3. Publish the description at a stable URL (for example `/api/v1/openapi.yaml`)
   and render it with any OpenAPI viewer.
4. State the terms of use, the rate limit, and a contact in the `info` block.
5. Test: a colleague who did not build the API retrieves one known value
   using only the description.

</Recipe>

   and run the governance checks in [chapter 8](./govern.mdx).

**What this does not do.** The example reads two CSV files and matches
words. A production server calls the office's API, paginates large
responses, returns the structure (code lists, dimensions) so the client can
form valid requests, handles disaggregations, caches, and runs behind
authentication and rate limits. The Data360 server below shows the fuller
tool set that results.

Two World Bank implementations exist. NADA exposes its catalog to AI
clients through an MCP interface, so an office that runs NADA has the
catalog side of this recipe with the software, next to NADA's REST API
(documented in OpenAPI). The [Data360 MCP server](https://github.com/worldbank/data360-mcp)
is a production example of the data side of this pattern. It exposes discovery tools
(`data360_search_indicators`, `data360_search_datasets`), metadata tools
(`data360_get_metadata`, `data360_get_disaggregation`), data tools
(`data360_get_data`, `data360_find_codelist_value`), and analysis tools,
over the Data360 API. The program's [MCP page](/docs/mcp/) describes the
architecture and the tools an MCP server for official statistics can expose.

</Recipe>

## Implementation options

- **Formats:** SDMX-CSV or SDMX-JSON for aggregate data; CSV with SDMX concept names and a table schema where SDMX tooling is not in place; Parquet for large files.
- **APIs:** the [SDMX REST API](https://sdmx.org/) for statistical data (the World Bank serves WDI this way), or a REST API described by [OpenAPI](https://www.openapis.org/), as the [Data360 API](https://data360.worldbank.org/en/api) is. Many offices already run one of these.
- **Identifiers:** persistent URLs, DOIs, or SDMX structure identifiers. Choose one scheme and keep it unchanged across site redesigns.
- **Agent interface:** the [Model Context Protocol](https://modelcontextprotocol.io/) is an open standard. A single MCP server can serve any compatible AI client. It wraps the API that already exists and does not replace it.
- **Documents:** when data exist only in PDFs, extraction tools can recover tables and figures. Publish the extracted data next to the document, and mark them as extracted.

## World Bank examples

- The [World Development Indicators SDMX API](https://datahelpdesk.worldbank.org/knowledgebase/articles/1886701-sdmx-api-queries) serves WDI through the SDMX 2.1 REST interface, and the [Data360 API](https://data360.worldbank.org/en/api) serves indicator search, metadata, and data.
- The [Data360 MCP server](https://github.com/worldbank/data360-mcp) exposes Data360 to AI clients through the Model Context Protocol.
- [Model Context Protocol for AI-centric data dissemination](/docs/mcp/) describes the architecture and the tools an MCP server for official statistics can expose.
- [Data Snapshots](https://arxiv.org/abs/2606.06242) covers layout detection models that locate figures and tables in PDF documents so that the data inside them can be extracted. The [home page](/) shows an example.

## Common mistakes

- **Publishing a PDF and calling it open data.** A table in a PDF cannot be requested by series and period. Publish the CSV next to it.
- **Wide layouts with one column per year.** Every release changes the columns. One row per observation keeps the schema stable.
- **Labels where codes belong.** "Q1 2025", "2025 Q1", and "2025-Q1" are three strings for one period. Codes in the file, labels in the code list.
- **Changing identifiers in a redesign.** Every citation and integration breaks. Keep identifiers and redirect old URLs.
- **An MCP server before an API.** The agent interface is a thin layer; the API and the data behind it are the work.

## How to test it

- **Direct request:** retrieve a known value with a single API call, written from the documentation alone, by someone who did not build the API.
- **Stability:** request the same identifiers a month later and confirm that they still resolve.
- **Completeness of response:** check that every response includes the unit, the period, and the source.
- **Agent check:** if an MCP server exists, ask an assistant for five known values and compare them with the official figures.
