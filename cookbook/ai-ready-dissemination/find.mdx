# 1. Make your statistics findable

**Question:** Can people and AI find our statistics?

## Why this matters

AI systems increasingly mediate how users discover data. A search assistant
looks at page titles, descriptions, and catalog records. A series with a vague
title, an empty description, or no machine-readable record may never appear in
the answer, even when it is the right series.

Users also describe what they need in their own words. "How many people go
hungry" and "prevalence of undernourishment" refer to the same topic, and a
keyword index treats them as unrelated.

## What good looks like

- Every dataset and indicator has a stable identifier and a complete record: title, description, unit, time coverage, geography, frequency, source, and contact.
- The catalog is published in a machine-readable form that crawlers and harvesters can read.
- Search finds results by meaning as well as by exact words, in the languages users use.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Fill in the description, unit, and coverage fields for every published series. Give each dataset its own page with a permanent URL. Publish an XML sitemap and a clear `robots.txt`. |
| **AI-ready** | Publish catalog records as DCAT or schema.org `Dataset` markup (JSON-LD) on each dataset page. Expose a catalog API or a harvestable feed. Add translated titles and descriptions for the main national and user languages. |
| **AI-native** | Add semantic search over the catalog using embeddings, combined with keyword search. Use AI to find and repair missing or inconsistent metadata, with human review. Offer the catalog to AI assistants through an agent interface (see [chapter 2](./retrieve.mdx)). |

:::info[Running example]
The example office has five series. One of them, `LF_UNEMP_PCT`, has no
description. The recipes below find that gap, publish each series as a
schema.org record, and add a search that understands "jobless rate".
:::

## Recipes

<Recipe title="1.1 Check the records against the schema and a completeness profile" level="Foundational" skills="Anyone who can export the catalog and run a Python script; a metadata lead to set the profile" time="Half a day the first time; minutes after that">

**Result:** for every series record, three answers: is it a valid instance
of the published schema, does it have every field the office requires at
its target level, and are the values well-formed. This is the first measure
to track, because every later step depends on these fields.

A completeness check has three layers, and they answer different questions:

| Layer | Question | Who decides the rule |
|---|---|---|
| Structure | Is the record a valid instance of the [World Bank metadata schema](https://github.com/worldbank/metadata-schemas) for its type? | The schema. The indicator schema requires only `idno` and `name`; the other 73 fields of `series_description` are optional. The other types are similar. |
| Completeness | Does the record have every field the office requires at this maturity level? | The office, in a **profile** file, one per data type. The schema does not define completeness. |
| Validity | Do dates parse, do periods run in order, are URLs URLs, do values come from the office's vocabulary, is the definition more than the name repeated? | Rules named in the profile and applied by the script. |

The same check runs for indicators, survey microdata, geospatial data,
documents, tables, scripts, images, and videos: the profile names the type,
the script fetches that type's schema. The [By data type](./data-types.md)
page lists the profiles and example records for each.

1. Export the records. A catalog that uses the schemas, through NADA or the
   Metadata Editor, exports nested JSON, which works for every type. For
   indicators, a CSV with one row per series also works: the
   [metadata template](pathname:///cookbook-files/ai-ready-dissemination/metadata_template.csv)
   shows the layout, and list fields such as `sources` and
   `geographic_units` take `;` between values.
2. Set the profile. Start from the profile for the type
   ([indicator](pathname:///cookbook-files/ai-ready-dissemination/profile_indicator.json),
   [microdata](pathname:///cookbook-files/ai-ready-dissemination/profile_microdata.json),
   [geospatial](pathname:///cookbook-files/ai-ready-dissemination/profile_geospatial.json),
   [document](pathname:///cookbook-files/ai-ready-dissemination/profile_document.json)).
   Each is a recommended default: it names the fields required at the
   foundational, AI-ready, and AI-native levels as paths into the record,
   gives the reason each field matters for AI-ready dissemination, and
   sets the validity rules (which fields are dates, which are URLs, which
   take a vocabulary, which need a minimum length). An office can remove a
   field from a level, and the reason states what that costs. Keep the
   edited profile in version control; it is the office's definition of
   "complete". Offices that document with the
   [Metadata Editor](https://github.com/worldbank/metadata-editor) can
   mirror the profile in its metadata templates, which set the required
   fields at entry time and validate records before they are published to
   NADA.
3. Run the check. It needs the `jsonschema` package (4.18 or later) for the
   structure layer and downloads the schema files the first time.

Output for the example catalog at the foundational level:

         5 of 5 records are valid instances of the schema
         Note: the schemas require little more than an identifier and a title. Validity is not completeness.

Layer 2  Completeness against profile 'recommended indicator profile', level 'foundational' (9 fields)
         4 of 5 records complete
         missing series_description.definition_long               in 1 record(s)

At `--level ai-ready` the same catalog has 0 of 5 records complete, with
`methodology`, `universe`, `series_break`, `limitation`, `license`,
`keywords`, `aliases`, and `contacts` missing from every record. That is the
normal result for a catalog that was documented for people and is now being
prepared for software, and it is the work list for the AI-ready level.

For the other types, the same command with the type's profile and a JSON
export:

```bash
python check_metadata.py example_microdata.json  profile_microdata.json  --level ai-ready
python check_metadata.py example_geospatial.json profile_geospatial.json
python check_metadata.py example_document.json   profile_document.json
```

4. Assign the incomplete records to a curator and set a date. Re-run the
   check monthly at the target level and keep the counts; the trend is the
   evidence that the catalog is improving.

**What this does not check.** Whether the definition is correct, whether the
name and the definition describe the same concept, whether the unit matches
the values, whether the text is specific enough to be useful, and whether
the keywords are the ones users search for. These are semantic checks. The
program's [Generative AI for Metadata Quality](/docs/metadata-quality/generative-ai-for-metadata-quality)
work scores records on completeness, semantic alignment, specificity, and
consistency with a language model and returns structured, auditable
results; the [Metadata Reviewer](/docs/metadata-reviewer/overview) puts
those suggestions in front of a curator. Run the three layers above first,
because a semantic check on records with empty fields has nothing to work
with.

</Recipe>

<Recipe title="1.2 Publish a schema.org Dataset record on every series page" level="AI-ready" skills="Web developer with access to the page template" time="Half a day for the template, then automatic">

Offices that run [NADA](https://nada.ihsn.org/) already have this: NADA
writes a schema.org `Dataset` block on every catalog page from the stored
record (the World Bank [Microdata Library](https://microdata.worldbank.org/)
pages show it), and the Metadata Editor can export schema.org, Croissant,
and DCAT from the same records. The steps below are for an office with its
own website.

   The required properties are `name`, `description`, and `url`; the others

```json file=../../website/static/cookbook-files/ai-ready-dissemination/dataset.jsonld
```

2. Insert the block in the page template inside a `script` element with
   `type="application/ld+json"`, filled from the catalog at render time.

software can emit [DCAT](https://www.w3.org/TR/vocab-dcat-3/) for the whole
catalog. DCAT and schema.org markup can coexist. For datasets that are
published for model training, [Croissant](https://mlcommons.org/croissant/)
extends the same schema.org record with the fields machine-learning tools
need to load the data.

<Recipe title="1.3 Add semantic search next to keyword search" level="AI-native" skills="Developer with Python; a server with a few GB of memory" time="One to two weeks including evaluation">

**Result:** search returns `LF_UNEMP_PCT` for "jobless rate" and
`FS_UNDERNOURISH_PCT` for "how many people go hungry", with the keyword
search still available for exact codes and names.

NADA provides semantic search over its catalog records, so an office that
runs it gets this layer with the catalog. The steps below are for an office
with its own search, and the evaluation in step 4 applies to both.

1. Build the question set and baseline scores first ([chapter 6](./evaluate.mdx)). Without them there is no way to tell whether the new search is better.
2. Embed each catalog record (title plus description) with a multilingual
   sentence-embedding model. Small open models run on a CPU for a catalog of
   a few thousand records.

```python
from sentence_transformers import SentenceTransformer, util

model = SentenceTransformer("intfloat/multilingual-e5-small")
records = [...]  # list of dicts with id, title, description
texts = ["passage: " + r["title"] + ". " + r["description"] for r in records]
index = model.encode(texts, normalize_embeddings=True)

def semantic_search(query, k=10):
    q = model.encode("query: " + query, normalize_embeddings=True)
    scores = util.cos_sim(q, index)[0]
    top = scores.argsort(descending=True)[:k]
    return [records[i]["id"] for i in top]
```

3. Combine the semantic ranking with the keyword ranking, for example by
   taking the best rank of each record across both lists. Keep the keyword
   path so that an exact identifier always wins.
4. Re-run the scoring script from chapter 6 and compare Recall@5 and MRR per
   language with the baseline. Keep the result with the date and model name.
5. Re-embed the catalog whenever records change, on a schedule.

**What this does not do.** The snippet embeds each record as one string and
ranks by cosine similarity. A production search also indexes the keyword
field and aliases, handles thousands of records with a vector index, filters
by topic and geography, re-ranks the top results, and logs queries for the
monthly review ([chapter 4](./ask.mdx)). General embedding models also
underperform on structured records with short labels, which is the problem
the fine-tuning work below addresses.

The program's [Data Discoverability](/docs/data-discoverability/) page
describes the approach in more detail, and the
[PI-FT pipeline](/pift-toolkit/pipeline) shows how to fine-tune an embedding
model on structured records when a general model is not good enough.

</Recipe>

## Implementation options

**Catalog records**

- The [World Bank metadata schemas](https://github.com/worldbank/metadata-schemas) define records for indicators, indicator databases, microdata (based on DDI Codebook), documents (Dublin Core), geospatial data (ISO 19115/19139), tables, images (IPTC), and scripts, with a DataCite block for DOIs. They come with a Python library and Excel templates.
- [NADA](https://nada.ihsn.org/), the open-source catalog that runs the World Bank Microdata Library, stores records in these schemas and supports DDI Codebook, Dublin Core, ISO 19115/19139, and IPTC.
- Each record gets a persistent identifier, with a DOI through [DataCite](https://schema.datacite.org/) where the office can register one ([chapter 5](./trust.mdx)).

**Machine-readable catalog metadata for the web**

- [DCAT](https://www.w3.org/TR/vocab-dcat-3/) (W3C) describes catalogs, datasets, and distributions. It is the base for many open data portals.
- [schema.org `Dataset`](https://schema.org/Dataset) markup in JSON-LD on dataset pages is read by general web crawlers and dataset search engines. [Croissant](https://mlcommons.org/croissant/) extends it for machine-learning datasets.
- [DDI](https://ddialliance.org/) describes surveys and microdata. [SDMX](https://sdmx.org/) describes aggregate statistical data and its structure.

**Search**

- Keyword search (BM25) remains valuable for exact codes, acronyms, and names.
- Dense retrieval with embedding models matches by meaning. Combining both usually gives the best results.
- Multilingual embedding models support queries in languages other than the one the metadata is written in. Translated metadata still improves results.

**Metadata quality**

- Start with a completeness report, then move to consistency: does the title describe the same thing as the definition?
- Use an LLM to draft missing descriptions or flag inconsistencies, and keep a person responsible for approval.

## World Bank examples

- The [metadata schemas](https://github.com/worldbank/metadata-schemas) of the Development Data Group define the record fields used in this chapter, and the [Microdata Library](https://microdata.worldbank.org/) runs on NADA with DDI records and DataCite DOIs.
- [Generative AI for Metadata Quality](/docs/metadata-quality/generative-ai-for-metadata-quality) scores indicator metadata on completeness, semantic alignment, specificity, and consistency.
- [Metadata Augmentation](/docs/metadata-augmentation/) groups survey variables into DDI-style themes.
- [Data Discoverability](/docs/data-discoverability/) describes semantic search over indicator catalogs, and the [PI-FT toolkit](/pift-toolkit/pipeline) fine-tunes embedding models for structured metadata.

## Common mistakes

- **Launching semantic search over incomplete metadata.** The model can only match what the record says. Recipe 1.1 comes first.
- **Redesigning the website and changing every URL.** Crawlers, citations, and AI systems lose the pages. Keep identifiers and set redirects for anything that must move.
- **Translating metadata by machine without review.** A wrong translation of a definition is worse than none. Translate titles first and have them checked.
- **Measuring once.** Scores drift as the catalog and models change. Keep the question set and re-run it.

## How to test it

- **Completeness:** the share of records that pass the schema and the office's profile at the target level, and the count of missing fields per field (recipe 1.1).
- **Known-item queries:** 30 to 50 queries for which you know the correct series, written the way users write. Check whether the correct series appears in the top 5 and top 10 ([chapter 6](./evaluate.mdx)).
- **Crawler view:** open a dataset page with a structured-data validator and confirm that the record is parsed.
- **Language check:** repeat the known-item queries in each supported language.
