# 9. Sustainability and maintenance

**Question:** Can we maintain what we build?

## Rationale

Pilots are easy to start and costly to keep running. Models change, vendors
change prices, and staff move on. An AI-ready dissemination system that depends
on one person or one provider can stop working within a year of launch.

## Target state

- The system is built from open standards and replaceable parts.
- Running costs are known and proportionate to the number of users.
- More than one person can operate and update each component.
- The metadata and data pipeline keeps working if the AI layer is switched off.

## Maturity levels

| Level | Steps |
|---|---|
| **Foundational** | Document how data and metadata are produced and published. Assign backups for each task. Improve metadata and file formats first, since these keep their value regardless of tools. |
| **AI-ready** | Use open standards for catalog, structure, and API (chapters 1 to 3). Keep code and configuration in version control. Schedule reviews of metadata and the test suite. Estimate the cost per query before launch. |
| **AI-native** | Use small and open models where they reach the needed quality, and larger models where the task requires them. Monitor cost, latency, and quality together. Share components with partner organizations, and contribute fixes back. |

:::info[Running example]
The example organization's catalog, API, and CSV files work with no AI component
running. The semantic search and the description drafts are an added layer:
each runs on a small open-weight model on one server, and each has a row in
the register with an exit plan.
:::

## Recipes

<Recipe title="9.1 Run the switch-off test" level="Foundational" skills="Operations" time="One hour">

**Result:** proof that the catalog, the API, and the downloads keep
working with every AI component stopped.

1. In a test environment, stop every AI component: the semantic search
   index, the assistant, the metadata drafting.
2. Check that series pages load, the API answers, bulk files download,
   and keyword search returns results.
3. Fix any dependency found. The authoritative data store and the API
   must never depend on the AI layer.
4. Repeat after any architecture change.

**What this does not do.** The switch-off test proves that the data
layer stands without the AI layer. The AI layer's own failure modes,
such as a model update that changes answers, are the evaluation
suite's to catch.

</Recipe>

<Recipe title="9.2 Estimate the cost per query before launch" level="AI-ready" skills="Developer; finance" time="Half a day">

**Result:** a cost per query that management can compare with the
expected number of users, and a basis for choosing between a hosted
model and a local one.

A hosted model is paid per token (roughly three quarters of a word)
sent and received. A local model costs a server and the staff to run
it, whatever the number of queries.

1. Measure, for 50 questions from the test set, the tokens sent and
   received per answer (including the retrieved records), and the time
   per answer.
2. For a hosted model, the cost per query is the input tokens times
   the input price plus the output tokens times the output price, at
   the provider's current prices. Add the share of fixed costs (search
   index, server) per expected query.
3. For a local model, the cost per query is the server cost per month
   plus the staff time for operation, divided by the expected queries
   per month.
4. Multiply by the expected queries per month, with a low and a high
   estimate.
5. Record the estimate with the date and the prices used. Revisit
   quarterly; prices and usage both change.

**What this does not do.** An estimate from fifty questions at today's
prices is a planning figure. Usage, prices, and tokens per answer all
change, the quarterly revisit is part of the recipe, and the measured
cost per query after launch replaces the estimate.

</Recipe>

<Recipe title="9.3 Choose the smallest model that passes the suite" level="AI-native" skills="Developer" time="One to three days per task">

**Result:** for each task, the smallest model that reaches the required
scores, with the scores of every model tried kept as evidence.

1. Set the required scores for the task from
   [chapter 6](./evaluate.mdx) before testing any model, for example
   Recall@5 of 0.85 per language for search, or 98% numeric accuracy
   for answers.
2. Test candidate models from small to large: a small open-weight model
   (one whose files the organization downloads and runs itself) first,
   then larger ones, then hosted models. Use the same questions and
   catalog for each.
3. Stop at the first model that meets the requirement, and record the
   scores of every model tried.
4. Repeat when a task changes, or once a year, since small models
   improve quickly.

The program's
[Efficient and Inclusive AI Applications](/docs/inclusive-ai/) page
compares model sizes by task and describes batch processing and locally
hosted models, and the
[small and open models cookbook](/cookbook/small-and-open-models/)
gives the full procedure.

**What this does not do.** The smallest model that passes the suite is
tested on what the suite covers. A new task needs new questions before
a smaller model is trusted on it, and the scores of the larger models
stay on file as the reference.

</Recipe>

## Implementation options

- **Architecture:** keep the AI layer separate from the authoritative data store and API. Place each component in the [GSBPM](https://unece.org/statistics/modernstats/gsbpm) phase it serves (the program's [GSBPM mapping](/docs/gsbpm-mapping) does this for its own workstreams), so that ownership follows the existing process.
- **Model size:** classification, tagging, and embedding tasks often work with small models. Open-weight models can run on one modest server.
- **Cost control:** cache repeated queries, batch non-urgent work such as metadata review, and set usage limits.
- **Skills:** a small team that combines a metadata specialist, a data engineer, and someone responsible for evaluation covers most of the work in this guide. Training material can be shared across organizations.
- **Lifecycle:** plan for model updates, index rebuilds, and the retirement of components. Re-run the evaluation suite after each.
- **Shared resources:** open-source tools and shared test sets let organizations reuse each other's work.

## World Bank examples

- [Efficient and Inclusive AI Applications](/docs/inclusive-ai/) compares model sizes by task and describes batch processing and local models.
- The program publishes its methods and software as open resources in the [GitHub repository](https://github.com/worldbank/ai4data).
- The [PI-FT deployment guide](/pift-toolkit/deployment) describes serving and refreshing a fine-tuned embedding model.

## Resources

- [GSBPM](https://unece.org/statistics/modernstats/gsbpm): the production model each AI component is placed in.
- [Efficient and Inclusive AI Applications](/docs/inclusive-ai/): model size by task, batch processing, and local open-weight deployment, the basis of recipes 9.2 and 9.3.
- [litellm](https://github.com/BerriAI/litellm): a provider-agnostic client that lets a model be replaced without rewriting the application.
- [Open LLM Leaderboard](https://huggingface.co/spaces/open-llm-leaderboard/open_llm_leaderboard) and [MTEB](https://huggingface.co/spaces/mteb/leaderboard): where to find candidate open-weight generation and embedding models to run through the suite.
- [Evaluation chapter](./evaluate.mdx): the suite that the switch-off test, the cost estimate, and the model choice all run against.

## Common mistakes

- **Choosing the largest model first.** It costs more at every query and hides whether a small one would do.
- **A pilot that lives on one laptop.** The handover test (below) finds this early.
- **No budget for re-running the evaluation.** Each model update needs a run; without it, quality drifts unnoticed.
- **Building what partner organizations already share.** Check the open resources first.

## Verification

- **Switch-off test:** recipe 9.1.
- **Handover test:** ask a staff member who did not build a component to run an update from the documentation.
- **Cost review:** compare monthly cost with the number of queries served, and review quarterly.
